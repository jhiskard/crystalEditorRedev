# UI 이식 품질 지침 (Legacy 1:1 Preservation)

- 작성일: 2026-04-30
- 위치: `webassembly/docs/phases/`
- 목적: 향후 어떤 Phase에서 UI 이식이 다시 필요하더라도, 최근 Phase 3.2 수준과 동일한 품질로 레거시 UI를 재현하기 위한 공통 실행 기준을 제공한다.

## 1. 적용 범위

- 대상: `webassembly/src/features/*` 하위의 모든 UI 이식 작업
- 기준 원본: `webassembly/src/legacy/*`의 동등 기능 UI
- 적용 시점: 새 Phase 계획서 작성 시점부터, 구현/검증/평가 전 과정

## 2. 절대 원칙 (변경 금지)

1. 레거시 UI의 옵션명, 표시 순서, 기본값, 입력 방식(checkbox/slider/combo/button), 유효 범위를 그대로 유지한다.
2. 모드 전환 방식(탭/콤보/라디오/메뉴 선택)은 레거시와 동일해야 한다.
3. 조건부 노출/비노출, 활성/비활성(grey-out) 규칙을 동일하게 유지한다.
4. Apply 시점(즉시 반영 vs 버튼 반영)을 동일하게 유지한다.
5. 공유 옵션은 레거시와 동일한 데이터 소스를 공유해야 한다.
6. ImGui ID 충돌이 없어야 하며, ID 충돌 회피 방식도 일관되게 적용한다.
7. "더 좋아 보이는 UI"로 임의 재설계하지 않는다. 기능 보존이 최우선이다.

## 3. 구현 절차 (필수 순서)

1. 레거시 기준 캡처
- 이식 대상 UI의 레거시 화면 캡처(빈 데이터/데이터 로드 상태 모두).
- 옵션 목록을 표로 추출: `옵션명 / 타입 / 기본값 / 범위 / 표시조건 / 반영시점 / 공유여부`.

2. UI 계약서 작성
- `legacy_ui_contract.md` 형태(Phase 문서 부록 또는 PR 본문)에 계약 표를 먼저 작성한다.
- 구현 시작 전 계약 표 누락 항목이 없어야 한다.

3. 상태 모델 매핑
- 레거시 옵션이 공유되는 경우, 공통 상태 구조체(예: `CommonRenderOptions`)로 먼저 모델링한다.
- 모드별 특화 옵션은 공통 옵션과 분리하되 렌더러 반영 경로는 분명히 나눈다.

4. 렌더/로직 분리
- UI 위젯 코드와 렌더 적용 코드를 분리한다.
- 레거시의 Direct Apply 동작은 이벤트 시점까지 동일해야 한다.

5. 레이아웃 복원
- 레거시가 테이블이면 테이블로, 그룹이면 그룹으로 동일 복원한다.
- Collapsing Header, 탭 등 구조를 임의 변경하지 않는다.

6. 데이터 의존성 훅 추가(테스트 목적)
- 데이터가 없어도 UI 이식 검증이 가능하도록 테스트 훅을 제공한다.
- 임시 훅은 `Sample Data`/`Demo Data` 성격으로 명시하고, 실제 파일 로드 경로와 구분한다.
- 훅은 `HasData()` 스위칭과 UI 활성화 검증에만 사용하며 실제 기능 구현 완료로 간주하지 않는다.

7. 다중 데이터 처리 복원
- 레거시에 다중 데이터 선택 UI(Mesh selector 등)가 있으면 반드시 복원한다.
- 선택 변경 시 연동되는 뷰어/렌더 상태까지 확인한다.

8. 색상/수치 도구 복원
- Level, +/- Value, Opacity 등 수치 항목 옆의 색상 선택 도구가 레거시에 있으면 반드시 포함한다.
- 색상 적용 경로(positive/negative/surface/plane)가 레거시와 동일해야 한다.

9. Slice/Plane 연동 복원
- Surface/Volume의 공통 옵션이 Slice Viewer Plane에 공유된다면 동일하게 연동한다.
- 레거시에 없는 컬러바 제어 항목은 새로 만들지 않는다.

10. ID 충돌 점검
- 모드 전환 UI에서 동일 label 사용 시 `##suffix` 정책으로 ID를 분리한다.
- Isosurface/Surface/Volumetric/Plane 간 충돌 가능 label을 사전 점검한다.

11. 런타임 시나리오 테스트
- S1: 빈 데이터 상태 UI 노출/비노출 규칙
- S2: 샘플 데이터 상태에서 모든 제어 조작
- S3: 실제 파일 로드 후 렌더 반영
- S4: 모드 전환 반복 시 상태 유지/초기화 규칙

12. 평가서 반영
- Phase 평가서에 `발견`, `분석`, `조치`, `잔여리스크`를 기록한다.
- 계획서 대비 일탈이 있으면 즉시 `Intentional UI deviation` 섹션에 사유를 남긴다.

## 5. 일탈(Deviation) 처리 규칙

- 허용 조건: 보안/플랫폼 제약/중대한 버그 회피로 인한 불가피한 경우만.
- 필수 기록:
  - 일탈 항목
  - 레거시 동작
  - 현재 동작
  - 일탈 사유
  - 사용자 영향
  - 원복 또는 후속 수정 계획(시점 포함)
- 기록 위치: 해당 Phase 계획서 + 평가서 모두.

## 6. 완료 기준 (Definition of Done)

- 레거시 대비 UI 계약서 항목 100% 매핑 완료.
- 검증 매트릭스 필수 항목(UI-01~UI-12) 중 "미수행" 없음.
- 콘솔 경고/오류 중 UI 이식 기인 이슈가 남아 있지 않음.
- 평가서에 변경 내역과 잔여 리스크가 최신 상태로 기록됨.

## 7. 향후 계획서 반영 방법

향후 Phase 계획서에는 아래 문구를 "공통 지침" 섹션에 포함한다.

> 본 Phase의 UI 이식은 `phases/phase_ui_porting_quality_guideline.md`를 준수한다.
> 계획서의 검증 매트릭스는 본 지침의 UI-01~UI-12를 최소 포함해야 한다.
> 레거시 대비 일탈이 발생하면 `Intentional UI deviation` 섹션에 즉시 기록한다.
